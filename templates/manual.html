1. Overview & Getting Started

Review Sentinel Prime (RSP) is a locally-run web application for systematic literature reviews (SLR). It helps researchers search, filter, monitor, and export scientific publications across 12 databases in a reproducible, PRISMA-compliant workflow.

Figure 1: RSP workflow — Search → Filter → Validate → Export → Publish

Key Features:

  • Search across 12 scientific databases simultaneously
  • Apply multi-level inclusion/exclusion criteria (year, type, language, terms, venues)
  • Validate completeness using known reference papers
  • Screen titles & abstracts manually — with optional local-LLM suggestions (human-in-the-loop)
  • Capture a Review Protocol (research questions, registration, methods) that auto-completes PRISMA items
  • Auto-generate PRISMA 2020 flow diagrams and evidence checklists
  • Export PRISMA-aligned replication packages (ZIP)
  • Schedule recurring searches for ongoing monitoring
  • Visualize results with publication-ready charts

Navigation:

Use the sidebar on the left of every page. Links are grouped logically:

  • Search — Run searches and view results
  • Saved Searches — Create, manage, and schedule searches
  • Results — Browse and download all local run snapshots
  • Screening — Title & Abstract (T&A) paper screening with Include / Exclude / Unsure decisions
  • Charts — Visualize search results
  • PRISMA — View the flow diagram and checklist
  • Settings — Configure API keys, SMTP email, run retention limits, and the AI Screening Assistant
  • Manual — This page
  • Feedback — Submit bug reports or feature requests
  • Research Survey — Research evaluation questionnaire
  • About — Version, credits, and optional support information

2. Running a Search

The Search page is the main interface for finding papers.

Figure 2: The Search interface — keywords field, action buttons row, and the database checkboxes split into “Ready to use — no API key” and “Requires an API key” (HAL, arXiv, ACM DL and OpenAlex checked by default)

Step-by-step:

1
Type your query in the keywords box using Boolean operators (OR, AND, parentheses). Click Query tips below the field for a quick guide.
2
Set Results per Page (default 25). This controls only how many papers are shown per page — RSP always retrieves up to 10,000 records per database regardless of this setting.
3
Select which databases to search. They are grouped by whether they need credentials: Ready to use — no API key (OpenAlex, HAL, arXiv, PubMed, ACM DL) and Requires an API key (Scopus, Web of Science, IEEE, ScienceDirect, Springer, Inspec, EBSCO). HAL, arXiv, ACM DL, and OpenAlex are checked by default; enable the others once their keys are configured in Settings. Saved-search state also restores previous database selections automatically.
4
Optionally, click "+ Show Inclusion / Exclusion Criteria" to add filters. The filter panel open/closed state now persists across refreshes.
5
Click Search Papers (or press Enter). A live progress panel appears, showing each database as it completes along with an elapsed timer. Alternatively, activate the Live Search mode toggle to switch to Offline Filter mode — this re-applies filters against a local cache without hitting the network.
6
Results appear below. Use the ▌▌ Cards / List toggle to switch between card and compact list views.

Live progress panel:

While the search runs, a progress panel shows each database being queried in real time. A elapsed timer tracks total search time. Errors (e.g., missing API key, rate limit) are shown inline per database without stopping the overall search.

Each database row shows X found, Y retrieved once it completes:

  • Found — total matching records reported by the API for your query
  • Retrieved — records actually downloaded (limited by your Max results setting). Retrieved will always be ≤ found.
  • Partial retrieval warning — if a database found more records than its API allowed RSP to download (a pagination limit, not your settings), the row shows an amber warning such as "Only 5,000 of 12,340 records retrieved (API pagination limit)". For a systematic review, treat this as a signal to narrow the query for that database — the identification count is otherwise incomplete.

Understanding results:

Each paper shows:

  • Title (clickable link to source)
  • Authors, Year, Venue
  • Source badge — colored label showing which database found it
  • DOI (if available)
  • Abstract preview (first 300 characters)
  • Keyword tags (if provided by the database)

View toggle (Cards / List):

After results load, a View: toggle bar appears above the results:

  • ▌▌ Cards — Full card layout with abstract, keywords, and a blue " View Paper" button (default)
  • List — Compact table (Source | Title | Year | Link). Click any title to expand inline details.

Buttons explained:

  • Search Papers — Execute the search against all selected databases in real time
  • Live Search — Toggle between Live Search (hits the network) and Offline Filter (re-filters the local cache without a network call). Useful for iterating filter criteria quickly.
  • Save Search — Save current configuration to Saved Searches
  • Import Config (JSON) — Reload all settings from a previously exported search_configuration.json file
  • Clear — Reset all fields and results after confirmation

After a search completes, an export bar appears below the result count:

  • Export Replication Package (ZIP) — Build and download the full PRISMA-aligned replication package
  • Export Config (JSON) — Download a search_configuration.json you can import later to replay this exact search
  • Print to PDF — Open a print-ready page of all results; use browser Print → Save as PDF
Tip: Your search state (keywords, filters, results) is automatically preserved in your browser. Navigate away and come back — everything stays as you left it.

3. Query Syntax Guide

RSP uses Boolean query syntax — the same syntax accepted by academic databases. Queries are passed directly to each database without modification.

Operators:

  • OR — return papers containing either term: deep learning OR neural network
  • AND — require both terms: machine learning AND software testing
  • Parentheses — group logic: (deep learning OR neural network) AND protein folding
  • Quotes — exact phrase: "systematic literature review"
  • NOT / AND NOT — exclude a term: machine learning AND NOT medical
Figure 3: Query syntax examples
Tip: A Query tips toggle appears directly below the keywords field on both the Search and Saved Searches pages. Click it for a quick-reference guide without leaving the page.
Note: Commas are not supported as query separators. Use OR to combine terms. If you enter a comma, an inline error message will prompt you to correct the query before searching.

5. Filters & Criteria

Click "+ Show Inclusion / Exclusion Criteria" on the Search page to expand the filter panel. Filters refine your results after retrieval from each database. They are applied in sequence — each step narrows the result set further.

Figure 4: Filter pipeline — screening, inclusion, and exclusion criteria applied in sequence

Year Range

Set "From" and/or "To" year to limit publications to a time window. Leave empty for all years.

Example: From 2018 To 2024 — only papers published between 2018 and 2024.

Document Types

Check one or more to include only those types:

  • Articles — Peer-reviewed journal papers
  • Conference — Conference proceedings
  • Thesis — PhD/Master dissertations
  • Book chapter — Chapters in edited volumes
  • Report — Technical/research reports
  • Preprint — Non-peer-reviewed preprints

Leave all unchecked → include all types.

Language

Select languages to include. Applies primarily to HAL. Leave unchecked for all languages.

Figure 5: The four color-coded filter cards — green for inclusion, red for exclusion. Each card has an ALL (AND) / ANY (OR) match mode dropdown inline with the label.

Include Terms green

Comma-separated keywords. Only papers whose title, abstract or author keywords contain these terms are kept in the results. Keywords are included so that records from connectors that return no abstract (e.g. Web of Science Starter) remain matchable.

Matching is case-insensitive and whole-word: the term art matches "art" but not "artificial". Multi-word terms match as phrases, and surrounding quotes are accepted — "machine learning" and machine learning behave the same.

Example: machine learning, neural network

Match mode:

  • ALL (AND) — paper must contain every listed term (default)
  • ANY (OR) — paper must contain at least one of the listed terms

Exclude Terms red

Comma-separated keywords. Papers whose title, abstract or author keywords match these terms are removed. The same case-insensitive, whole-word matching as Include Terms applies.

Example: survey, review, grey literature

Match mode:

  • ALL (AND) — paper is removed only if it contains all listed terms
  • ANY (OR) — paper is removed if it contains any of the listed terms (default)

Include Venues green

Comma-separated journal/conference name fragments. Only papers from matching venues are kept. Matching is case-insensitive and partial, against the publication venue name only (journal or conference) — the name of the source database is never considered, so a fragment like IEEE matches "IEEE Transactions on Software Engineering" but does not blanket-match every record retrieved from IEEE Xplore. Leave empty to include all venues.

Example: TSE, ICSE, JSS, TOSEM, EMSE

Match mode: ALL (AND) requires the venue name to contain every fragment; ANY (OR) keeps papers whose venue matches at least one fragment (default).

Exclude Venues red

Comma-separated journal/conference name fragments. Papers from matching venues are removed. Like Include Venues, only the publication venue name is matched — to exclude an entire database (e.g. all of arXiv), uncheck that database in Select Databases instead.

Example: workshop, poster, preprint

Match mode: same logic as Exclude Terms — ALL (AND) removes only if all fragments match; ANY (OR) removes if any fragment matches (default).

Tip: Defaults differ per card: Include Terms defaults to ALL (AND) (every term must appear), while Exclude Terms, Include Venues, and Exclude Venues default to ANY (OR). Keep Include Venues on ANY when listing multiple distinct venues (e.g. TSE, ICSE) — no paper can be in all of them simultaneously.
Tip: Apply filters progressively. After each change, check your Validation Papers to ensure no relevant papers were accidentally excluded.

6. Validation Papers

Validation Papers let you verify that your search criteria are comprehensive enough by tracking whether known-relevant papers appear in your results.

Figure 6: Validation panel — green = found in results, red = missing (criteria may be too restrictive)

How to use:

1
Click "+ Validation Papers" to expand the panel
2
Paste a known paper title and click Add
3
Repeat for all reference papers you want to track (5–15 recommended)
4
Run a search — the panel shows green (found) or red (missing) for each
5
If papers turn red after adding filters, your criteria may be too strict
Tip: Title matching is fuzzy — minor punctuation variations still match. Validation papers are saved with your search configuration when you use "Save Search". The validation panel open/closed state now also persists across refreshes and saved search restores.

7. Saved Searches & Scheduling

Saving from the Search page:

  1. Configure your search (keywords, databases, filters)
  2. Click the green Save Search button
  3. Enter a name, choose a schedule, and confirm
  4. All settings (query, databases, filters, validation papers, and panel visibility state) are saved

Managing Saved Searches:

Navigate to Saved Searches to view and manage all your searches. Each card shows the query, databases, schedule, last run status, and — for scheduled searches — a live countdown to the next run.

Figure 7: A scheduled saved search — schedule badge, live countdown timer, last run status, and action buttons
  • Run Now — Execute the search immediately and store results
  • Edit — Modify query, databases, filters, schedule, or notification email
  • Delete — Remove the saved search and its history

Scheduling:

Set a schedule when creating or editing a search:

  • Manual — only runs when you click "Run Now"
  • Every N hours — e.g., every 6 hours
  • Every N days — e.g., every 2 days
  • Every N months — N calendar months after the last run (e.g. a run on 15 March with "Every 1 month" next fires on 15 April)

All intervals are anchored to the last run, so restarting the application does not reset the countdown.

Countdown Timer:

Every scheduled search displays a live countdown timer showing exactly how long until the next automatic run:

  • The timer is anchored to the real lastRun timestamp stored on the server (or createdAt if the search has never run), so it is always accurate — even after refreshing the page or navigating away and returning.
  • Format adapts to the remaining time — e.g., 2d 4h 11m for days, 5h 30m 12s for hours, 48m 07s for minutes.
  • When the countdown reaches zero it switches to Running soon… in amber.
  • The page polls the server every 30 seconds in the background. If a scheduled run fires while the page is open, the timer resets automatically to the new interval — no page refresh required.
Tip: The countdown resets correctly after every run. If you click Run Now and then refresh the page, the timer restarts from the full interval based on the new lastRun timestamp.
Note: Scheduled searches only run while the application is running. If a run was due while the app was stopped, it fires shortly after the next startup (anchored to the stored last-run time) instead of waiting a full interval.

8. Email Notifications & Diff

RSP can automatically email you after each scheduled run with a summary of what changed since the previous run.

Enabling notifications:

1
When creating or editing a saved search, set the schedule to any automatic interval (not Manual)
2
Enter an email address in the Notify by email field
3
Configure SMTP in Settings (host, port, username, password)

What the email contains:

  • Run timestamp — when the search was executed
  • Change summary — e.g. "+3 new, -1 removed" or "No changes since last run"
  • New papers highlighted in green — rows with a NEW badge
  • Removed papers section — papers that were in the previous run but not this one
  • CSV attachment — full result list with a Status column (new, existing, removed)

SMTP configuration:

Go to Settings → Email / SMTP section and fill in:

  • Host — e.g. smtp.gmail.com
  • Port — typically 587 (TLS) or 465 (SSL)
  • Username — your email address
  • Password — your email password or App Password
Gmail users: You must use a Google App Password (not your regular password). Enable 2-step verification on your account first, then generate an App Password at myaccount.google.com/apppasswords.
Tip: On the first run, all papers are labelled "first run" in the CSV — there is no previous run to compare against. From the second run onward, the diff comparison is active.

9. T&A Screening

The Screening page provides a structured Title & Abstract screening workflow. It lets you review papers one by one and record an Include, Exclude, or Unsure decision for each — the standard first screening step in a Systematic Literature Review.

Figure 8: Screening page — run picker (top card) and the decision panel with Include / Exclude / Unsure buttons. The purple AI suggestion box and "Ask AI" button appear only when the AI Screening Assistant is enabled in Settings.

Loading papers to screen:

The Screening page opens with a run picker. Two options are available:

  • Open Selected Run — Choose a saved run from the dropdown and click to load it. This loads the filtered paper list from that saved snapshot.
  • Use Last Search (memory) — Loads papers from the most recent search held in your browser's memory (no saved run required).

Making screening decisions:

1
Each paper is shown with its title, authors, year, venue, and abstract. Review each paper's title and abstract carefully.
2
Click one of the three decision buttons: Include, Exclude, or ? Unsure. The active decision is highlighted with a deeper colour.
3
Navigate with the ← Prev / Next → arrow buttons. A progress counter (e.g. Paper 3 / 42) tracks where you are.
4
Decisions are saved automatically in your browser as you go — you can leave the page and return without losing progress.

Action buttons:

  • Reset All — Clear all decisions after confirmation (irreversible)
  • Export CSV — Download a CSV of all papers with their screening decision (include, exclude, unsure, or undecided)
Tip: Use the Unsure category for borderline papers — you can review them separately or in a second pass. The Export CSV will include all decisions so you can filter and audit later.

AI Screening Assistant (optional):

When enabled in Settings → AI Screening Assistant, two extra controls appear:

  • Ask AI (decision panel) — asks the configured local LLM to suggest Include / Exclude / Unsure for the current paper, with a one-sentence reason and a confidence score. The suggestion appears in a purple box; nothing is saved until you click Accept suggestion or decide manually.
  • AI-suggest unscreened (toolbar) — fetches suggestions for every unscreened paper in batches, so they are already waiting as you step through the queue.

Decisions accepted from a suggestion are recorded with AI-assisted provenance and the model name. The PRISMA checklist (item 8, Selection process) automatically discloses how many decisions were AI-assisted and by which model — the disclosure most journals now require. The prompt sent to the LLM includes your Review Protocol research questions and eligibility criteria, so filling in the protocol first improves suggestion quality.

Workflow note: T&A Screening is typically done after running a search and reviewing the PRISMA numbers. Use it to document manual screening decisions that are not automatically applied by RSP's filter criteria.

10. Results Hub

The Results page is a central archive of all local run snapshots — both ad-hoc searches you ran from the Search page and scheduled automatic runs triggered by saved searches.

Figure 9: Results Hub — each run shows its type badge, query, timestamp, paper count, and a Download ZIP button

Run types:

  • Saved blue badge — Run was triggered by a saved search (manual "Run Now" or automatic schedule)
  • Ad-hoc grey badge — Run was done directly from the Search page without saving

Each entry shows:

  • Run name and truncated query string
  • Timestamp — date and time the search was executed
  • Paper count — total papers in the result set
  • Download ZIP — Download the full PRISMA-aligned replication package for that run
Run retention: RSP stores a configurable number of recent snapshots locally. Older runs are automatically pruned once the limit is reached. Adjust the limit in Settings → Run Retention.
Tip: Use the Results Hub to compare snapshots over time if you are running scheduled searches. Each ZIP is a self-contained replication package — ideal for open science deposits.

11. PRISMA Flow Diagram

The PRISMA page automatically generates a PRISMA 2020-compliant flow diagram and interactive evidence checklist based on your last search results.

Figure 10: PRISMA flow diagram — all stage cards and excluded side cards are clickable to show the paper list

Features:

  • Auto-generated from your latest search — all filter stages are visualised automatically
  • Per-database chips at the top — click any database chip to see its retrieved papers in the panel below
  • Clickable stage cards — click any main flow box (Identification, Deduplication, Screening, Eligibility, Included) to open the paper list panel with Cards / List view toggle
  • Clickable removed/excluded cards — the red side boxes (Duplicates removed, Screening excluded, Eligibility excluded) are also clickable and show the actual papers that were removed at that stage
  • Sub-criteria pills below each stage show which filters were active and how many papers each removed
  • Manual Review Steps — add post-inclusion steps (full-text review, snowballing, etc.) that appear as new boxes in the flow and can also remove papers
  • Export Diagram as PNG — captures the full rendered diagram exactly as it appears on screen
  • Review Protocol form — capture review-level facts no search can infer (research questions, rationale, outcomes, registration record, reviewer team, synthesis and risk-of-bias methods, funding, competing interests). Saved server-side, exported as 03_protocol/review_protocol.json in the replication package, and used to auto-complete the corresponding checklist items
  • PRISMA 2020 Evidence Checklist — interactive 27-item checklist (39 entries including sub-items) with AUTO (up to 27 entries auto-assessed from your search data and Review Protocol, including a drafted structured abstract and process-limitations statement) and MANUAL (12 entries requiring study-content analysis) modes, with progress bar and localStorage persistence

Clickable cards — paper list panel:

Clicking any flow card opens a Paper Panel below the diagram showing all papers at that stage. The panel supports:

  • ▌▌ Cards — Full card layout with title, authors, year, abstract preview, DOI and a " View Paper" button
  • List — Compact table with expandable rows
  • Pagination — 20 papers per page with Prev / Next navigation
Note: Excluded paper lists (Duplicates, Screening, Eligibility cards) are populated when a search is run with the current version of RSP. If you see "No paper details available", run a new search to enable this feature.

Adding manual review steps:

Below the diagram, the Manual Review Steps panel lets you add steps that occur after automated filtering (e.g., manual full-text review by two researchers, backward snowballing). Each step specifies:

  • Step name — e.g. "Manual Full-Text Review"
  • Added — papers added at this step (e.g. from snowballing)
  • Removed — papers excluded at this step
  • Description — optional note (e.g. "Reviewed by 2 independent researchers")

Steps appear as new purple cards in the flow diagram, with a red side card if any papers were removed. Use the ↑ ↓ arrows to reorder steps, and to remove them.

PRISMA 2020 Evidence Checklist:

All 27 official PRISMA 2020 items (39 entries including sub-items) are listed with two modes:

  • AUTO — up to 27 entries assessed from your search data and Review Protocol: eligibility criteria, per-database sources with search dates and retrieval warnings, search strategy, selection process (including AI-assistance disclosure), excluded studies with sample citations per reason, plus auto-drafted structured-abstract and process-limitations statements. Items marked partial show your draft with a notes box — review, edit, and check off.
  • MANUAL — the remaining entries require reading study content (risk-of-bias results, per-study outcomes, synthesis results, interpretation) — check the box and type your response in the text area

A progress bar shows how many items have been addressed. Notes are saved automatically to your browser (localStorage) and persist across page refreshes. Use Reset inputs to clear all manual entries, or Export PNG to download the checklist as an image.

12. Charts & Visualizations

After running a search, the Charts page shows visual summaries of your results.

Available charts:

  1. Publications per Year — Bar chart with trend line (green = increasing, red = decreasing) and average line. Displayed taller than default for better year-by-year readability.
  2. Abstract Keyword Frequency — Horizontal bar chart of the most frequent terms extracted from paper abstracts. Use the Source dropdown to filter by database and the Top N dropdown to change how many terms are shown.
  3. Publications per Venue — Horizontal bar chart showing the top 20 publishing venues (journals and conferences).
  4. Publications per Document Type — Bar chart breaking down results by article, conference paper, preprint, etc.

Expanding a chart:

Each chart card has a expand button in the top-right corner. Clicking it opens the chart fullscreen in a modal overlay. Close with ×, click the dark backdrop, or press Escape.

Exporting:

Each chart has an Export as PNG button that downloads a publication-ready image.

Tip: Charts reflect the last search you ran. Run a new search to update the charts.

13. Export & Replication Package

RSP can generate a complete, PRISMA-aligned SLR Replication Package for open science repositories.

Export as ZIP:

After running a search, an Export Replication Package (ZIP) button appears. The ZIP is named <search_name>_<date>.zip and contains the following structure:

Figure 11: Replication package folder structure

Key files explained:

  • 01_search_strategy/search_configuration.json — Machine-readable record of the full search setup (query, databases, filters, validation papers, results summary). Same format as the Export Config (JSON) button.
  • search_configuration.json (root) — Identical importable copy. Drag this directly onto the Import Config (JSON) button on the Search page to replay the exact search.
  • 02_data/initial_search_results.csv — All papers retrieved before deduplication and filtering.
  • 02_data/deduplicated_records.csv — Papers after duplicate removal.
  • 02_data/included_studies.csv — Final included papers after all filters.
  • 02_data/excluded_studies.csv — Papers removed by filters, with exclusion reasons.
  • 02_data/screening_decisions.csv — Per-paper Title & Abstract screening decisions with reasons, plus ai_assisted and ai_model columns recording where the AI assistant was involved (included when screening was performed; pulled from the server run record even if your browser copy is missing).
  • 02_data/prisma_data.json — PRISMA stage counts in JSON for programmatic use.
  • 03_protocol/protocol.md — Prose description of the search protocol (IC/EC criteria).
  • 03_protocol/review_protocol.json — Machine-readable Review Protocol (research questions, registration, reviewer team, synthesis/RoB methods) when filled in on the PRISMA page.
  • 04_images/ — Server-generated prisma_flow_diagram.svg (always included, T&A screening stage included when performed) plus chart and PRISMA PNG exports if captured before export.
  • 05_evidence_checklist/PRISMA_evidence_checklist.txt — Auto-assessed PRISMA 2020 checklist. It is generated last, so every artefact row is marked [OK] or [--] according to what the ZIP actually contains, and it reports per-reason exclusion counts, title & abstract screening totals, identification split between databases and citation searching, validation seed-paper recall, any AI automation used, and a list of items still needing manual attention.
  • README.md — Human-readable summary of the package for open science repositories.

PRISMA & Checklist PNG export:

On the PRISMA page:

  • Export Diagram as PNG — captures the entire rendered flow diagram exactly as it appears on screen (including all cards, excluded side cards, sub-criteria pills, and manual steps) at 2× resolution for crisp print quality
  • Export PNG (Checklist card) — exports the PRISMA 2020 Evidence Checklist as a PNG image
Tip: The diagram PNG captures what is currently visible — if you have added Manual Review Steps, they appear in the export too. The PNG is also auto-saved to your browser on page load so the Replication Package ZIP can include it.
Tip: The root-level search_configuration.json can be dropped directly into the Import Config (JSON) button on the Search page to instantly reload all search settings and replay the exact same search.

14. Settings & API Keys

The Settings page is organised into four collapsible sections — click a section header to expand or collapse it:

  • Database API Keys — Configure keys for each database that requires one
  • Email Notifications (SMTP) — Configure outgoing mail for scheduled-run alerts and survey/feedback submissions
  • Run Retention (Local Storage) — Set how many saved and ad-hoc run snapshots are kept locally; run cleanup immediately
  • AI Screening Assistant (Local LLM) — Point RSP at a local LLM (e.g. Ollama) or any OpenAI-compatible endpoint to get Include/Exclude/Unsure suggestions during Title & Abstract screening. Suggestions are never applied automatically: you review and accept each one, and accepted decisions record the model name so PRISMA item 8 can disclose the automation tool. With a local Ollama instance, titles and abstracts never leave your computer. Cloud providers also work through their OpenAI-compatible endpoints — OpenAI (https://api.openai.com), Anthropic Claude (https://api.anthropic.com), and Google Gemini (https://generativelanguage.googleapis.com/v1beta/openai) — but note that titles and abstracts are then sent to that provider
Quick access: When a Feedback submission (or a Survey submission that could not be delivered) cannot be sent, the modal includes a "Configure SMTP in Settings" button. Clicking it takes you directly to Settings and automatically expands the SMTP section so you can set it up without hunting for it.
Run retention quick access: Open Settings → Run Retention to set how many saved and ad-hoc run snapshots are kept locally and to run cleanup immediately.

For each database that requires a key:

1
Obtain a free API key from the database's developer portal (links are shown on each card)
2
Go to Settings → expand Database API Keys → find the database card
3
Paste your key into the input field. The Test Connection button activates as soon as text is detected, and stays active for databases that already have a saved key — testing with an empty field verifies the stored key.
4
Click Save Key. The key is saved immediately and a connection test runs automatically — the card turns green on success or red on failure, and a Last checked timestamp is displayed. You can also click Test Connection at any time to re-run the check with the stored key.
How Test Connection works: All API tests run through the app's backend server to avoid browser security restrictions (CORS). Results include the exact error code and a direct link to the provider's developer portal if your key is rejected. Every card preserves the last result and timestamp so you can see which services were verified most recently.
Automatic connection checks: When you open the Settings page, databases that do not require a key — HAL, arXiv, PubMed (optional key), and ACM Digital Library (optional key) — are tested automatically in the background every time the page loads. Their cards update with a live result and a fresh Last checked timestamp without any button click. Key-required databases (IEEE, Scopus, etc.) are also auto-tested on page load when a key is already saved, and again automatically after you click Save Key — so you always see the result immediately without a separate click.

15. Research Evaluation Survey

The Research Survey page contains a structured research evaluation questionnaire designed for academic user studies assessing RSP's usability and impact.

Survey structure:

  • Section A — Participant Background: Optional demographic info (role, experience, field)
  • Section B — System Usability (SUS): 10 questions on a 1–5 Likert scale, based on Brooke (1996)
  • Section C — Perceived Usefulness & Ease of Use: 8 questions on a 1–7 scale, based on TAM/UTAUT
  • Section D — Impact on Research Quality: 7 questions on transparency, reproducibility, and bias
  • Section E — Feature-Specific Evaluation: 5 questions rating individual features
  • Section F — Open Feedback: 5 free-text questions for qualitative insights

How it works:

  • A progress bar at the top tracks how many Likert questions have been answered (30 total)
  • All required questions must be answered before submission
  • Clicking Submit Survey validates the form and sends the responses to the study's response collector:
    • Responses are recorded regardless of whether SMTP is configured, so participants can submit on a fresh installation
    • SMTP configured — the study owner additionally receives an email with the full response attached as a CSV
    • If the submission cannot be delivered — a modal offers " Open in My Email App" (opens Outlook, Apple Mail, Gmail, etc. with all responses pre-filled) or " Configure SMTP in Settings" so nothing is lost
  • Clicking Start Over resets all fields after confirmation
Tip: The survey is designed for ethics-approved user studies. All responses are anonymous unless the participant voluntarily provides identifying information.

16. Bug Reports & Feature Requests

The Feedback page lets users report issues or propose new ideas for RSP.

Submission types:

  • Bug Report — Report something that isn't working as expected. Additional fields appear for steps to reproduce, expected behaviour, and actual behaviour.
  • Feature Request — Propose a new feature or improvement. The bug-specific fields are hidden.

Form fields:

  • Title / Short Summary (required) — A brief description of the issue or idea
  • Detailed Description (required) — Full explanation
  • Steps to Reproduce (bug only) — How to trigger the issue
  • Expected Behaviour (bug only) — What should happen
  • Actual Behaviour (bug only) — What actually happens
  • Impact / Priority — Low, Medium, or High
  • Your Email (optional) — For follow-up communication

Buttons:

  • Start Over — Resets all fields after confirmation
  • Submit — Validates required fields, then submits the report:
    • The report is recorded in the project’s issue-collection form regardless of whether SMTP is configured, so feedback works on a fresh installation
    • SMTP configured — the maintainer additionally receives an email copy of the report
    • If no delivery method is available — a modal appears offering: “ Open in My Email App” (opens your default email client with the report pre-filled) or “ Configure SMTP in Settings” (takes you to Settings with the SMTP section auto-expanded)

17. SLR Workflow Best Practices

Follow this recommended workflow for a systematic literature review using RSP:

Figure 12: Recommended SLR workflow with RSP

Key principles:

  • Start broad, then narrow — Begin with no filters, add criteria progressively
  • Always validate — Use validation papers as your ground truth after every change
  • Monitor PRISMA — Click the stage cards and excluded cards to inspect exactly which papers were removed at each stage
  • Document post-inclusion steps — Use Manual Review Steps on the PRISMA page to capture full-text review and snowballing in the flow diagram
  • Complete the checklist — Fill in all 12 MANUAL items on the PRISMA Evidence Checklist before exporting
  • Save early, save often — Save your search configuration for reproducibility
  • Export everything — The replication package ensures your review is fully reproducible

Performance notes:

  • Retrieval is capped at 10,000 records per database, and some APIs impose lower pagination ceilings — RSP shows an amber partial-retrieval warning in the progress panel when a database could not deliver everything it found. Narrow the query for that database if completeness matters
  • arXiv has rate limiting — a 3-second delay between result pages is applied automatically; avoid rapid consecutive searches
  • HAL supports more server-side filters (language, doc type, year) which are faster than post-filtering
  • Searches stream results database by database via SSE — you see progress live as each database completes

Data storage:

  • Search form state & results — browser localStorage (persists across navigation)
  • Excluded paper lists — browser localStorage (lastExcludedDocs) — enables clickable PRISMA excluded cards
  • PRISMA manual steps & checklist notes — browser localStorage (persists across page refreshes)
  • Validation papers — browser localStorage
  • Saved searches & history — server-side JSON files in data/ folder
  • API keys — server-side files in data/ folder (never leave your machine)
Need help? RSP is designed to be self-explanatory. Each page includes contextual hints. If you encounter issues, restart the application with python app.py and check the terminal for error messages.
Community support: RSP is free and will remain free. If it helps your work, optional support is available via the footer link and on the About page.
