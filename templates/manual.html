1. Overview & Getting Started

Review Sentinel Prime (RSP) is a locally-run web application for systematic literature reviews (SLR). It helps researchers search, filter, screen and export publications across 12 databases. The researcher remains responsible for verifying coverage, evidence and PRISMA reporting.

Figure 1: Example workflow — Search → Filter → Screen → Review PRISMA → Export. Validate the search and review evidence throughout.

Key Features:

  • Search across 12 scientific databases simultaneously
  • Apply multi-level inclusion/exclusion criteria (year, type, language, terms, venues)
  • Validate completeness using known reference papers
  • Extend the result set with forward/backward citation snowballing (OpenAlex)
  • Screen titles & abstracts manually — with optional AI suggestions from a local or online model (human-in-the-loop)
  • Record full-text decisions and reasons per run, with optional two-reviewer screening and adjudication in either stage
  • Capture a Review Protocol (research questions, registration, methods) that supplies evidence for PRISMA items
  • Auto-generate PRISMA 2020 flow diagrams and evidence checklists
  • See per database whether retrieval was complete, partial or failed — never a silent 0 — with a per-database search log exported alongside the results
  • Export PRISMA-aligned replication packages (ZIP)
  • Schedule recurring searches for ongoing monitoring
  • Visualize results with publication-ready charts

Navigation:

Use the sidebar on the left of every page. Links are grouped logically:

  • Search — Run searches and view results
  • Saved Searches — Create, manage, and schedule searches
  • Results — Browse and download all local run snapshots
  • Screening — Title & Abstract (T&A) decisions, with links to full-text and optional two-reviewer screening for a run
  • Charts — Visualize search results
  • PRISMA — View the flow diagram and checklist
  • Settings — Configure API keys, retrieval limits, the AI Screening Assistant, SMTP email and run retention
  • Manual — This page
  • Feedback — Submit bug reports or feature requests
  • Research Survey — Research evaluation questionnaire
  • About — Version, credits, and optional support information

2. Running a Search

The Search page is the main interface for finding papers.

Figure 2: The Search interface — keywords field, action buttons row, and the database checkboxes split into “Ready to use — no API key” and “Requires an API key” (HAL, arXiv, ACM DL and OpenAlex checked by default)

Step-by-step:

1
Type your query in the keywords box using Boolean operators (OR, AND, parentheses). Click Query tips below the field for a quick guide.
2
Set Results per Page (default 25). This controls only how many papers are displayed per page. The separate per-database retrieval limits are configured in Settings → Retrieval; provider and connector limits can stop retrieval earlier.
3
Select which databases to search. They are grouped by whether they need credentials: Ready to use — no API key (OpenAlex, HAL, arXiv, PubMed, ACM DL) and Requires an API key (Scopus, Web of Science, IEEE, ScienceDirect, Springer, Inspec, EBSCO). HAL, arXiv, ACM DL, and OpenAlex are checked by default; enable the others once their keys are configured in Settings. Saved-search state also restores previous database selections automatically.
4
Optionally, click "+ Show Inclusion / Exclusion Criteria" to add filters (terms and venues can be separated by commas or one per line; keep a phrase that contains a comma in double quotes). The filter panel open/closed state now persists across refreshes.
5
Click Search Papers (or press Enter). A live progress panel appears, showing each database as it completes along with an elapsed timer. Alternatively, activate the Live Search mode toggle to switch to Offline Filter mode — this re-applies filters against a local cache without hitting the network.
6
Results appear below. Use the ▌▌ Cards / List toggle to switch between card and compact list views.

Live progress panel:

While the search runs, a progress panel shows each database being queried in real time. A elapsed timer tracks total search time. Errors (e.g., missing API key, rate limit) are shown inline per database without stopping the overall search.

Each database row shows X found, Y retrieved once it completes:

  • Found — total matching records reported by the API for your query
  • Retrieved — records actually downloaded. Retrieved will always be ≤ found. Each database has an adjustable maximum in Settings → Retrieval; provider limits and connector safeguards can stop retrieval earlier.
  • Partial retrieval warning — if a database found more records than RSP could download (a maximum reached, an API paging limit or an error part-way), the row shows an amber warning such as "RSP retrieval cap of 1,000 records reached; the API reported 12,340". For a systematic review, treat this as a signal to act: apply the year range at the database or raise the maximum (Settings → Retrieval), or narrow the query — the identification count is otherwise incomplete.

When the search finishes, a Database coverage table stays under the result count (and is restored when you come back to the page). Each database is marked:

  • Complete — every record the API reported was retrieved
  • Partial — some records were retrieved but not all: an error part-way, an API paging limit, RSP's per-database retrieval cap, or an empty page from the API
  • Failed — nothing was retrieved (missing key, network error, rate limit or quota, rejected query). A database that reports matches but returns none is always shown as failed, never as "0 results"

Records from a Partial database are kept: they appear in the results, exports and PRISMA as usual, and only the missing part is reported. For your final PRISMA numbers, use a run in which every database is Complete.

Figure 3: The Database coverage table shown after every search — status, records reported by each API, retrieved, and included after filters, with the reason for any partial or failed database

RSP retries rate-limited (HTTP 429) and server (5xx) responses, timeouts and network errors with increasing waits, honouring the API's Retry-After header, and keeps each API's documented page size and request rate. When a daily or weekly quota is used up, the database is marked failed with the time until it resets. The same status appears on the PRISMA database chips and, for scheduled searches, as "incomplete coverage" on the Saved Searches card and in the notification email.

Understanding results:

Each paper shows:

  • Title (clickable link to source)
  • Authors, Year, Venue
  • Source badge — colored label showing which database found it
  • DOI (if available)
  • Abstract preview (first 300 characters)
  • Keyword tags (if provided by the database)

View toggle (Cards / List):

After results load, a View: toggle bar appears above the results:

  • ▌▌ Cards — Full card layout with abstract, keywords, and a blue " View Paper" button (default)
  • List — Compact table (Source | Title | Year | Link). Click any title to expand inline details.

Buttons explained:

  • Search Papers — Execute the search against all selected databases in real time
  • Live Search — Toggle between Live Search (hits the network) and Offline Filter (re-filters the local cache without a network call). Useful for iterating filter criteria quickly.
  • Save Search — Save current configuration to Saved Searches
  • Import Config (JSON) — Reload all settings from a previously exported search_configuration.json file
  • Clear — Reset all fields and results after confirmation

After a search completes, an export bar appears below the result count:

  • Export Replication Package (ZIP) — Build and download the full PRISMA-aligned replication package
  • Export Config (JSON) — Download a search_configuration.json you can import later to replay this exact search
  • Print to PDF — Open a print-ready page of all results (source, title, authors, year, venue, DOI); use browser Print → Save as PDF. Print to PDF + Abstracts produces the same page with each paper's abstract added (a much longer PDF)
Tip: Your search state (keywords, filters, results) is automatically preserved in your browser. Navigate away and come back — everything stays as you left it.

3. Query Syntax Guide

RSP uses Boolean query syntax — the same syntax accepted by academic databases. RSP normalises Boolean operators to uppercase and translates your query into each database's own syntax before sending it (for example, wildcards inside quoted phrases are removed for arXiv and OpenAlex).

Operators:

  • OR — return papers containing either term: deep learning OR neural network
  • AND — require both terms: machine learning AND software testing
  • Parentheses — group logic: (deep learning OR neural network) AND protein folding
  • Quotes — exact phrase: "systematic literature review"
  • NOT / AND NOT — exclude a term: machine learning AND NOT medical
Figure 4: Query syntax examples
Tip: A Query tips toggle appears directly below the keywords field on both the Search and Saved Searches pages. Click it for a quick-reference guide without leaving the page.
Note: Commas are not supported as query separators. Use OR to combine terms. If you enter a comma, an inline error message will prompt you to correct the query before searching.

Query check before searching:

When you start a live search, RSP checks the query — and every exclude term — before contacting any database. If something would make the databases reject it, the search does not start and a message says exactly what to fix, for example "Please fix your search query before searching: Search query: 1 opening parenthesis '(' is not closed."

  • Always checked: a quotation mark " that is not closed; a ( without its ) or the reverse; empty parentheses (); AND / OR / NOT at the end of the query or before a ); AND / OR at the start or right after another operator (e.g. AND OR).
  • Checked when Scopus is selected (Scopus rejects these, other databases may accept them): && / || (use AND / OR), "phrase"~5 (use NEAR/5), +term / -term (use AND / NOT), and Web of Science field tags such as TI= or TS=.
  • Still allowed: NOT at the start and AND NOT, wildcards (automat*), NEAR/3, hyphenated words (COVID-19, e-learning), and brackets inside a quoted phrase.

Re-filtering from the local cache (Offline Filter mode) skips the check, because no database is contacted. If Scopus still rejects a query, its row in the coverage table reads "Scopus could not read the search query (HTTP 400)" with the same list of things to check.

5. Filters & Criteria

Click "+ Show Inclusion / Exclusion Criteria" on the Search page to expand the filter panel. Filters refine your results after retrieval from each database. They are applied in sequence — each step narrows the result set further.

Figure 5: Filter pipeline — screening, inclusion, and exclusion criteria applied in sequence

Year Range

Set "From" and/or "To" year to limit publications to a time window. Leave empty for all years. By default the year range is applied by RSP after download, so PRISMA lists every paper it removed; to apply it at the database instead (useful when a database reaches its retrieval cap), see Settings → Retrieval.

Example: From 2018 To 2024 — only papers published between 2018 and 2024.

Document Types

Check one or more to include only those types:

  • Articles — Peer-reviewed journal papers
  • Conference — Conference proceedings
  • Thesis — PhD/Master dissertations
  • Book chapter — Chapters in edited volumes
  • Report — Technical/research reports
  • Preprint — Non-peer-reviewed preprints

Leave all unchecked → include all types.

Language

Select languages to include. Applies primarily to HAL. Leave unchecked for all languages.

Figure 6: The four color-coded filter cards — green for inclusion, red for exclusion. Each card has an ALL (AND) / ANY (OR) match mode dropdown inline with the label.

Include Terms green

Keywords separated by commas or one per line. Only papers whose title, abstract or author keywords contain these terms are kept in the results. Keywords are included so that records from connectors that return no abstract (e.g. Web of Science Starter) remain matchable.

Matching is case-insensitive and whole-word: the term art matches "art" but not "artificial". Multi-word terms match as phrases, and surrounding quotes are accepted — "machine learning" and machine learning behave the same. A phrase still matches when a line break falls inside it in the abstract. Keep a phrase that contains a comma in double quotes (e.g. "safety, security") so it is not split.

Example: machine learning, neural network

Match mode:

  • ALL (AND) — paper must contain every listed term (default)
  • ANY (OR) — paper must contain at least one of the listed terms

Exclude Terms red

Keywords separated by commas or one per line. Papers whose title, abstract or author keywords match these terms are removed. The same case-insensitive, whole-word matching as Include Terms applies.

Example: survey, review, grey literature

Match mode:

  • ALL (AND) — paper is removed only if it contains all listed terms
  • ANY (OR) — paper is removed if it contains any of the listed terms (default)

Include Venues green

Comma-separated journal/conference name fragments. Only papers from matching venues are kept. Matching is case-insensitive and partial, against the publication venue name only (journal or conference) — the name of the source database is never considered, so a fragment like IEEE matches "IEEE Transactions on Software Engineering" but does not blanket-match every record retrieved from IEEE Xplore. Leave empty to include all venues.

Example: TSE, ICSE, JSS, TOSEM, EMSE

Match mode: ALL (AND) requires the venue name to contain every fragment; ANY (OR) keeps papers whose venue matches at least one fragment (default).

Exclude Venues red

Comma-separated journal/conference name fragments. Papers from matching venues are removed. Like Include Venues, only the publication venue name is matched — to exclude an entire database (e.g. all of arXiv), uncheck that database in Select Databases instead.

Example: workshop, poster, preprint

Match mode: same logic as Exclude Terms — ALL (AND) removes only if all fragments match; ANY (OR) removes if any fragment matches (default).

Tip: Defaults differ per card: Include Terms defaults to ALL (AND) (every term must appear), while Exclude Terms, Include Venues, and Exclude Venues default to ANY (OR). Keep Include Venues on ANY when listing multiple distinct venues (e.g. TSE, ICSE) — no paper can be in all of them simultaneously.
Tip: Apply filters progressively. After each change, check your Validation Papers to ensure no relevant papers were accidentally excluded.

6. Validation Papers & Citation Snowballing

Validation Papers let you verify that your search criteria are comprehensive enough by tracking whether known-relevant papers appear in your results.

Figure 7: Validation panel — green = found in results, red = missing (criteria may be too restrictive)

How to use:

1
Click "+ Validation Papers" to expand the panel
2
Paste a known paper title and click Add
3
Repeat for all reference papers you want to track (5–15 recommended)
4
Run a search — the panel shows green (found) or red (missing) for each
5
If papers turn red after adding filters, your criteria may be too strict
Tip: Title matching is fuzzy — minor punctuation variations still match. Validation papers are saved with your search configuration when you use "Save Search". The validation panel open/closed state now also persists across refreshes and saved search restores.

Citation snowballing:

Below the Validation Papers panel, + Citation Snowballing extends your results by following citations from a few key "seed" papers. It uses OpenAlex (free, no API key).

1
Click "+ Citation Snowballing" to expand the panel
2
Enter a seed paper's DOI (e.g. 10.1145/3519939) or its title and click Add. Titles are matched to the top OpenAlex result, and the resolved title is shown so you can check it. Up to 20 seeds are used per run
3
Choose a Direction: Forward (papers that cite the seeds), Backward (papers cited by the seeds — up to the first 50 references of each seed) or Both directions
4
Click Run Snowballing. New papers are merged into the current results (duplicates by DOI or title are skipped), tagged with a Snowball↑Forward / Snowball↓Backward source, and added to the PRISMA identification counts. Clear Snowball Results removes them again

Seeds are stored with a saved search and in the exported configuration, and are restored when you reload either. Snowballing itself runs only when you click Run Snowballing on the Search page. To record citation searching done elsewhere (hand-search, grey literature), use the Snowballing / Other Sources panel on the PRISMA page (section 11).

7. Saved Searches & Scheduling

Saving from the Search page:

  1. Configure your search (keywords, databases, filters)
  2. Click the green Save Search button
  3. Enter a name, choose a schedule, and confirm
  4. All settings (query, databases, filters, validation papers, and panel visibility state) are saved

Managing Saved Searches:

Navigate to Saved Searches to view and manage all your searches. Each card shows the query, databases, schedule, last run status (including ⚠ incomplete coverage when a database failed or was only partly retrieved — hover to see which), and — for scheduled searches — a live countdown to the next run.

Figure 8: A scheduled saved search — schedule badge, live countdown timer, last run status, and the Run Now / Results / Edit / Delete buttons
  • Run Now — Execute the search immediately and store results
  • Results — Show the stored results of the last run in a panel below the list
  • Edit — Modify query, databases, filters, schedule, or notification email
  • Delete — Remove the saved search and its history

Scheduling:

Set a schedule when creating or editing a search:

  • Manual — only runs when you click "Run Now"
  • Every N hours — e.g., every 6 hours
  • Every N days — e.g., every 2 days
  • Every N months — N calendar months after the last run (e.g. a run on 15 March with "Every 1 month" next fires on 15 April)

All intervals are anchored to the last run, so restarting the application does not reset the countdown.

Countdown Timer:

Every scheduled search displays a live countdown timer showing exactly how long until the next automatic run:

  • The timer is anchored to the real lastRun timestamp stored on the server (or createdAt if the search has never run), so it is always accurate — even after refreshing the page or navigating away and returning.
  • Format adapts to the remaining time — e.g., 2d 4h 11m for days, 5h 30m 12s for hours, 48m 07s for minutes.
  • When the countdown reaches zero it switches to Running soon… in amber.
  • The page polls the server every 30 seconds in the background. If a scheduled run fires while the page is open, the timer resets automatically to the new interval — no page refresh required.
Tip: The countdown resets correctly after every run. If you click Run Now and then refresh the page, the timer restarts from the full interval based on the new lastRun timestamp.
Note: Scheduled searches only run while the application is running. If a run was due while the app was stopped, it fires shortly after the next startup (anchored to the stored last-run time) instead of waiting a full interval.

8. Email Notifications & Diff

RSP can automatically email you after each scheduled run with a summary of what changed since the previous run.

Enabling notifications:

1
When creating or editing a saved search, set the schedule to any automatic interval (not Manual)
2
Enter an email address in the Notify by email field
3
Configure SMTP in Settings (host, port, username, password)

What the email contains:

  • Run timestamp — when the search was executed
  • Change summary — e.g. "+3 new, -1 removed" or "No changes since last run"
  • Incomplete coverage notice — when a database failed or was only partly retrieved, a banner names it, because its papers may otherwise appear as "removed"
  • New papers highlighted in green — rows with a NEW badge
  • Removed papers section — papers that were in the previous run but not this one
  • CSV attachment — full result list with a Status column (new, existing, removed)

SMTP configuration:

Go to Settings → Email / SMTP section and fill in:

  • Host — e.g. smtp.gmail.com
  • Port — typically 587 (TLS) or 465 (SSL)
  • Username — your email address
  • Password — your email password or App Password
Gmail users: You must use a Google App Password (not your regular password). Enable 2-step verification on your account first, then generate an App Password at myaccount.google.com/apppasswords.
Tip: On the first run, all papers are labelled "first run" in the CSV — there is no previous run to compare against. From the second run onward, the diff comparison is active.

9. T&A Screening

The Screening page provides a structured Title & Abstract screening workflow. It lets you review papers one by one and record an Include, Exclude, or Unsure decision for each — the standard first screening step in a Systematic Literature Review.

Figure 9: Screening page — run picker (top card) and the decision panel with Include / Exclude / Unsure buttons. The purple AI suggestion box and "Ask AI" button appear only when the AI Screening Assistant is enabled in Settings.

Loading papers to screen:

The Screening page opens with a run picker. Two options are available:

  • Open Selected Run — Choose a saved run from the dropdown and click to load it. This loads the filtered paper list from that saved snapshot.
  • Use Last Search (memory) — Loads papers from the most recent search held in your browser's memory (no saved run required).

Making screening decisions:

1
Each paper is shown with its title, authors, year, venue, and abstract. Review each paper's title and abstract carefully.
2
Click one of the three decision buttons: Include, Exclude, or ? Unsure. The active decision is highlighted with a deeper colour. Include and Unsure are recorded immediately; Exclude opens a Reason row — pick a preset (or Custom reason…) and click Confirm. Full-text exclusions and their reasons are recorded separately for PRISMA item 16b.
3
Navigate with the ← Prev / Next → buttons, jump to the next undecided paper with Next Unscreened, or type a number in Go to. A progress bar with included / excluded / unsure / unscreened counts tracks where you are.
4
Decisions are saved automatically as you go — on the server when you opened a saved run (so they are included in that run's exports), or in your browser when you used Use Last Search (memory). You can leave the page and return without losing progress.

Summary tab:

Switch from Screen Papers to Summary for a table of every paper with its decision and reason. Filter it by All / Included / Excluded / Unsure / Unscreened, search by title, and jump back to any paper from its row.

Action buttons:

  • Reset All — Clear all decisions after confirmation (irreversible)
  • Export CSV — Download a CSV of all papers with their screening decision (include, exclude, unsure, or unscreened), plus reason and timestamp
Tip: Use the Unsure category for borderline papers — you can review them separately or in a second pass. The Export CSV will include all decisions so you can filter and audit later.

Full-text screening:

Open Full-text screening from a run in Results, its T&A screen, or its PRISMA page. Only papers included in that run's server-saved title and abstract screening are candidates; browser-memory screening alone cannot supply candidates. Open each report, select Include, Exclude, Not retrieved or Unsure, and save. Exclusions and non-retrieval require a reason. Pending and unsure reports remain distinct from included reports.

Figure 9b: Simplified full-text screening page. Save each decision; the reason field is required for exclusions and reports not retrieved.

If a T&A decision changes, a no-longer-eligible full-text decision is retained but excluded from current counts. Duplicate or missing DOI/title identities must be resolved before screening that record. Changes make previous checklist confirmations stale; review and reconfirm them. The workflow does not screen manually entered other-source counts. If manual review steps already represent full-text screening, adjust them to avoid double counting.

Two-reviewer screening (optional):

From either screening page of a saved or ad-hoc run, select Two-reviewer screening before recording any decisions in that stage. Enter two distinct reviewer labels and enable the mode separately for title and abstract and for full text. The labels and mode cannot be changed afterwards. Existing single-reviewer decisions are not converted; use a new run if the stage already has decisions.

Each reviewer selects their label and records a decision. Matching definite decisions are resolved automatically; disagreements or any unsure decision require an adjudicator to enter a final decision and explanation. Exclusions and non-retrieval require reasons. Editing a review invalidates any adjudication, and unresolved papers do not count as included. A paper must have a resolved title and abstract inclusion to be eligible for full-text screening. Previous decisions remain in the run's audit history and replication ZIP as 02_data/two_reviewer_screening.json.

Important: Reviewer labels are self-declared; the app does not authenticate reviewers or enforce blinding. Both decisions are visible, so researchers must arrange independent assessment themselves and accurately describe their actual process. AI suggestions are not available in two-reviewer mode.

AI Screening Assistant (optional):

When enabled in Settings → AI Screening Assistant, two extra controls appear:

  • Ask AI (decision panel) — asks the configured AI model to suggest Include / Exclude / Unsure for the current paper, with a one-sentence reason and a confidence score. The suggestion appears in a purple box; nothing is saved until you click Accept suggestion or decide manually.
  • AI-suggest unscreened (toolbar) — fetches suggestions for every unscreened paper in batches, so they are already waiting as you step through the queue.

Decisions accepted from a suggestion are recorded with AI-assisted provenance and the model name; whenever the AI made a suggestion, what it suggested and its confidence are kept even if you decided differently. Under the progress bar, the page shows how often your decisions matched the AI (percentage and Cohen's κ). The PRISMA checklist (item 8, Selection process) automatically discloses how many decisions were AI-assisted, by which model, and the reviewer–AI agreement — the disclosure most journals now require. See Privacy notice, estimates and record-keeping for details. The prompt sent to the LLM includes your Review Protocol research questions and eligibility criteria, so filling in the protocol first improves suggestion quality.

Workflow note: T&A Screening is typically done after running a search and reviewing the PRISMA numbers. Use it to document manual screening decisions that are not automatically applied by RSP's filter criteria.

10. Results Hub

The Results page is a central archive of all local run snapshots — both ad-hoc searches you ran from the Search page and scheduled automatic runs triggered by saved searches.

Figure 10: Results Hub — saved and ad-hoc runs offer screening, full-text screening, download and deletion actions when available.

Run types:

  • Saved Search blue badge — Run was triggered by a saved search (manual "Run Now" or automatic schedule)
  • Ad-hoc grey badge — Run was done directly from the Search page without saving

Each entry shows:

  • Type badge and timestamp — when the search was executed
  • The query string
  • Counts — Found (reported by the databases), Included (after filters), the databases searched, the saved-search ID, and a screened badge showing T&A screening progress
  • Download ZIP — Download a snapshot of that run: run.json, included_docs.csv, raw_docs.csv, excluded_docs.json, summary.json, search_log.csv/search_log.json (the per-database retrieval log) and, if screening was done, screening_decisions.csv
  • View Details — Expand the run to see its settings and eligibility summary
  • Screen — Open an ad-hoc or saved run in T&A Screening; Full-text screening opens its full-text decisions
  • Download JSON — Download the raw run record
  • Delete — Remove the run after confirmation

The toolbar at the top has Refresh and Open Results Folder (opens the local folder in your file manager).

Run retention: RSP stores a configurable number of recent snapshots locally. Older runs are automatically pruned once the limit is reached. Adjust the limit in Settings → Run Retention.
Tip: Use the Results Hub to compare snapshots over time if you are running scheduled searches. For a full PRISMA-aligned replication package, use Export Replication Package (ZIP) on the Search page (section 13).

11. PRISMA Flow Diagram

The PRISMA page generates a flow diagram and interactive PRISMA 2020 evidence checklist from the selected run or latest search. Researchers must verify the counts and confirm reporting in their manuscript.

Figure 11: Simplified flow. T&A and full-text stages appear when recorded; not-retrieved records do not have a downloaded paper list.

Features:

  • Auto-generated from your latest search — all filter stages are visualised automatically
  • Removed before retrieval — appears below Identification when some records were counted by the databases but not downloaded: outside the date range (when the year range is applied at the database, see Settings → Retrieval) or not retrieved (retrieval cap or API error — the run is incomplete). A Records retrieved box follows, so identified − removed before retrieval = retrieved
  • Per-database chips at the top — click any database chip to see its retrieved papers in the panel below
  • Clickable stage cards — click any main flow box (Identification, Deduplication, Screening, Eligibility, Included) to open the paper list panel with Cards / List view toggle
  • Clickable removed/excluded cards — the Duplicates, Screening and Eligibility side boxes show available removed papers. Records removed before retrieval were not downloaded, so there is no paper list for them.
  • Sub-criteria pills below each stage show which filters were active and how many papers each removed
  • Snowballing / Other Sources — record backward and forward snowballing, other sources (hand-search, grey literature) and the number excluded after T&A screening; these appear as a parallel card at the Identification stage
  • Manual Review Steps — add other post-filter steps as flow boxes. Do not duplicate decisions already recorded in full-text screening.
  • Export Diagram as PNG — captures the full rendered diagram exactly as it appears on screen
  • Review Protocol form — capture review-level facts no search can infer (research questions, rationale, outcomes, registration record, reviewer team, synthesis and risk-of-bias methods, funding, competing interests). Saved server-side, exported as 03_protocol/review_protocol.json in the replication package, and used as checklist evidence
  • PRISMA 2020 Evidence Checklist — interactive 27-item checklist (39 entries including sub-items). AUTO EVIDENCE entries show recorded data or drafts; all entries require researcher confirmation. Save notes and confirmations with the corresponding search run.
  • Guided completion and consistency checks — expand Guided completion to see questions for unconfirmed items; open an item to add notes and explicitly confirm it. Checks flag incomplete database retrieval, inconsistent recorded flow counts, pending or unsure screening decisions, missing recorded exclusion reasons, and invalid other-source or manual-step counts. They use the data available on this page and do not verify manuscript reporting or replace researcher review.

Clickable cards — paper list panel:

Click a stage or supported exclusion card to open the Paper Panel below the diagram. Availability depends on the recorded run; not every summary has individual paper details. The panel supports:

  • ▌▌ Cards — Full card layout with title, authors, year, abstract preview, DOI and a " View Paper" button
  • List — Compact table with expandable rows
  • Pagination — 20 papers per page with Prev / Next navigation
Note: Excluded paper lists (Duplicates, Screening, Eligibility cards) are populated when a search is run with the current version of RSP. If you see "No paper details available", run a new search to enable this feature.

Snowballing / Other Sources panel:

Below the diagram, enter the number of records found by backward snowballing, forward snowballing and other sources, plus those excluded after T&A screening, add an optional note, and click + Save. Use this for citation searching or hand-searching done outside RSP; snowballing run from the Search page (section 6) is already counted automatically.

Adding manual review steps:

Below the diagram, the Manual Review Steps panel lets you add steps after automated filtering. Avoid duplicating decisions or other-source counts already recorded elsewhere. Each step specifies:

  • Step name — e.g. "Manual Full-Text Review"
  • Added — papers added at this step (e.g. from snowballing)
  • Removed — papers excluded at this step
  • Description — optional note (e.g. "Reviewed by 2 independent researchers")

Steps appear as new purple cards in the flow diagram, with a red side card if any papers were removed. Use the ↑ ↓ arrows to reorder steps, and to remove them.

Manual steps and other-source counts are saved with the selected run on the server. If older browser data exists, use the appropriate Import older data button after checking that it belongs to this run. Import is available when the run's manual evidence is empty and does not delete the browser copy. If another tab changes the evidence first, reload before saving again. A saved run ID is required.

PRISMA 2020 Evidence Checklist:

All 27 official PRISMA 2020 items (39 entries including sub-items) are listed with two modes:

  • AUTO EVIDENCE — up to 29 entries show information or drafts from search data and the Review Protocol. These do not establish that the corresponding item has been reported; verify the report, add notes and explicitly confirm each item.
  • MANUAL — the remaining entries require researcher input, such as study-content analysis. Add notes and confirm after verifying the report.

Open a run's checklist from Results, or use the latest run on the PRISMA page. Add notes, confirm items after checking the report, and select Save checklist; unsaved edits are not included in exports. A run ID is required for saving. The progress bar counts current confirmations only. Use Refresh evidence to check for changes: a changed search, screening decisions, protocol, or local context may mark confirmations stale. Review and reconfirm those items, then save. Import older notes copies browser-wide notes into empty items without importing checkmarks. Reset inputs clears the current inputs after saving; Export PNG downloads an image.

Saved checklists and manual evidence belong to individual runs and are deleted when their run is deleted or pruned. The Review Protocol is shared across runs, so changing it can make confirmations stale in multiple runs. Changes to a run's manual evidence can also make confirmations stale. The replication ZIP includes saved notes and statuses; when the matching evidence context is unavailable, confirmations are marked unverified rather than assumed current.

14. Settings & API Keys

The Settings page is organised into five collapsible sections — click a section header to expand or collapse it:

  • Database API Keys — Configure database credentials. Cards are grouped by required credentials, optional keys and no-key connections; the Elsevier institutional token is optional. A connection issues badge counts cards with failed connection checks.
  • Retrieval — Apply the year range at the database, and set the maximum records downloaded from each database (see Retrieval settings below)
  • AI Screening Assistant — Get Include/Exclude/Unsure suggestions during Title & Abstract screening from a model running on your own computer or an online service. Suggestions are never applied automatically: you review and accept each one, and accepted decisions record the model name so PRISMA item 8 can disclose the automation tool. See Setting up the AI Screening Assistant below.
  • Email Notifications (SMTP) — Configure outgoing mail for scheduled-run alerts and survey/feedback submissions
  • Run Retention (Local Storage) — Set how many saved and ad-hoc run snapshots are kept locally; run cleanup immediately
Quick access: When a Feedback submission (or a Survey submission that could not be delivered) cannot be sent, the modal includes a "Configure SMTP in Settings" button. Clicking it takes you directly to Settings and automatically expands the SMTP section so you can set it up without hunting for it.

Setting up the AI Screening Assistant

  1. Open Settings → AI Screening Assistant and set Assistant to Enabled.
  2. Under Where should the AI run? pick an option. The page shows step-by-step instructions for it:
    • Ollama or LM Studio — runs on a computer you control; titles and abstracts are sent to the configured model server, which may be on another computer in your network. Install the app, download a model, and (LM Studio) start its server in the Developer tab. No API key needed.
    • OpenAI, Anthropic, Google Gemini, Groq, OpenRouter — online services. Paste your API key (the page links to where to create one). Titles and abstracts are sent to that provider, and usage is billed to your account. Anthropic (Claude) is connected through Anthropic's own API: its answers are always valid include / exclude / unsure JSON, and it is asked for a quick, low-effort answer to keep screening fast and cheap.
    • Other / custom server — any OpenAI-compatible or Ollama-compatible server; enter its address and, if needed, an API key.
  3. Choose a Model. The list fills in automatically with the models installed (local) or available (online); use Refresh list after installing a new one, or Other — type a name… for anything not listed.
  4. Click Test & Save. RSP sends a short test message to the model; settings are saved only if it answers correctly. If not, a plain-language message explains what to fix (server not running, wrong IP, rejected API key, model not found, out of credit, too slow).
Switching is quick: each option remembers its own address, model, and API key. To switch between, say, Ollama and OpenAI, just pick it again and click Test & Save — the Screening page always uses the last saved option.

Privacy notice, estimates and record-keeping

  • Privacy notice: the first time you use an online AI service, RSP asks you to confirm that titles, abstracts, your search query and your screening criteria will be sent to that provider. It asks once per service. Local servers (Ollama, LM Studio, your own network) never trigger it.
  • Estimate before a batch: AI-suggest unscreened first shows how many papers will be sent, the expected time and, for online services, a rough cost range. These are rules of thumb, not measurements. During the run, the button shows progress and the time left.
  • Record-keeping: whenever the AI made a suggestion, the decision records the vendor, the model, what the AI suggested and its confidence. This is kept even if you decided differently. It appears in screening_decisions.csv (columns ai_vendor, ai_suggested, ai_confidence), so you can report AI use and check how often it agreed with you.
  • Agreement on screen: under the progress bar, the Screening page shows how often your decisions matched the AI (percentage and Cohen's κ).
  • Automatic retry: if the AI's reply can't be read, RSP asks once more with a stricter instruction before reporting an error for that paper. (With Claude this does not happen: the answer format is enforced. If an older Claude model doesn't support that, RSP automatically falls back to a plain request.)
  • Model download: with Ollama selected, Settings offers a Download button for the recommended models (Qwen 2.5 7B, Gemma 3 12B, Gemma 3 27B).
  • API keys: keys are stored as plain text in data/ai_config.json (the other database keys are also in data/). Don't share, sync or commit the data folder.

The export package also includes 02_data/risk_of_bias_template.csv (one row per included study, with domain columns for the tool chosen in the protocol: RoB 2, ROBINS-I, CASP or generic) and 02_data/grade_certainty_template.csv (one row per protocol outcome) to fill in for PRISMA items 18, 21 and 22.

Choosing between local and online, and which model

  • Local (Ollama / LM Studio): sends paper details to the configured server on a computer you control; speed depends on its hardware.
  • Online (OpenAI, Gemini, Anthropic, Groq, OpenRouter): fast and needs no special hardware, but titles and abstracts are sent to the provider and you pay per paper.
  • Local models by graphics memory: none or 8 GB: Qwen 2.5 7B / Llama 3.1 8B; 12–16 GB: Gemma 3 12B / Qwen 2.5 14B / Phi-4; 24 GB+: Gemma 3 27B / Qwen 2.5 32B / Mistral Small 24B.
  • Online models: the small, fast tiers — OpenAI “mini”, Gemini “Flash”, Claude “Haiku”, Groq Llama 70B.
  • Avoid: reasoning/“thinking” models (DeepSeek-R1, QwQ, o-series) and models of 3B or less. Current Claude models also think before answering, but RSP asks them for low effort, so they stay fast.
  • In Settings, the model list marks recommended models with ★ and ones to avoid with ⚠. Model names change over time, so always use Refresh list.
  • Before relying on a model, screen about 50 papers yourself and compare its agreement with your decisions.

Using Ollama on another computer

RSP can run on one computer while Ollama runs on another (for example a laptop with a large model) on the same home or office network.

On the computer running Ollama (Windows):

  1. Allow network access: open PowerShell, run setx OLLAMA_HOST 0.0.0.0, then quit Ollama (tray icon → Quit) and start it again. (macOS/Linux: set the same OLLAMA_HOST environment variable for the Ollama service.)
  2. Allow port 11434 through the firewall: in PowerShell as Administrator run
    New-NetFirewallRule -DisplayName "Ollama" -Direction Inbound -Protocol TCP -LocalPort 11434 -Action Allow -Profile Private
    and make sure the network is set to Private (Settings → Network & internet).
  3. Find its IP address: run ipconfig and note the IPv4 Address, e.g. 192.168.1.50.

On the computer running RSP:

  1. Check the connection: open http://192.168.1.50:11434 in a browser — it should say "Ollama is running".
  2. In Settings → AI Screening Assistant choose Ollama, set Server address to http://192.168.1.50:11434, click Refresh list, pick the model, and click Test & Save.
Keep in mind: both computers must be on the same network, and the Ollama computer must be awake with Ollama running while you screen. If its IP address changes, update the server address (or reserve a fixed IP for it in your router). LM Studio works the same way: enable Serve on Local Network in its server settings and use port 1234 (http://192.168.1.50:1234/v1).
Docker: inside the container localhost is the container itself — to reach Ollama / LM Studio on the same computer use http://host.docker.internal:11434 or http://host.docker.internal:1234/v1.
Security: Ollama has no password and traffic is not encrypted, so anyone on the same network can use it. Only do this on a trusted home or office network — never on public Wi-Fi.
Privacy: AI settings, including API keys, are stored locally in data/ai_config.json. Keys are never shown again in the browser; don't share your data/ folder. Large local models (e.g. 30B+) can be slow without a strong GPU — choose a smaller model if suggestions time out.

Retrieval settings

Apply the year range at the database (off by default). Normally RSP downloads every year and removes records outside your Year range afterwards, so the PRISMA diagram lists each removed paper. Retrieval limits can fill up with years you later discard. With this option on:

  • The Year range is sent to each database, so only records inside it are downloaded.
  • One extra count-only request per database records the all-years total, so Records identified keeps the same meaning.
  • PRISMA shows a Removed before retrieval — outside the date range box with the count per database. There is no paper list for it, because those records are never downloaded.
  • RSP still checks years locally. If a database returns many records outside the range, the coverage table warns that it may have ignored the limit. Databases define "year" differently (arXiv uses the submission date), so a few records may still be removed locally.

Use it when the Database coverage table shows Partial — retrieval cap reached. If every database shows Complete, leaving it off gives the same numbers plus the list of removed papers.

Maximum records per database. Choose 500–10,000 records for each database. The default is 1,000 for IEEE Xplore, Scopus, Inspec, ScienceDirect, Springer Nature, PubMed and ACM, and 10,000 for the others. The page shows approximate request counts and known restrictions. Provider quotas and connector paging safeguards can stop retrieval below the selected maximum: for example, ScienceDirect stops at 5,000, EBSCO at 50 pages, and Web of Science at 20 Starter or 50 Expanded pages. Increasing a maximum does not guarantee complete retrieval. Missing records are reported as Partial and appear in PRISMA as Not retrieved.

Run retention quick access: Open Settings → Run Retention to set how many saved and ad-hoc run snapshots are kept locally and to run cleanup immediately.

For each database that requires a key:

1
Obtain a free API key from the database's developer portal (links are shown on each card)
2
Go to Settings → expand Database API Keys → find the database card
3
Paste your key into the input field (Web of Science also asks for the edition; EBSCO asks for User ID, Password and Profile ID, with a Save Credentials button). The Test Connection button activates as soon as text is detected, and stays active for databases that already have a saved key — testing with an empty field verifies the stored key.
4
Click Save Key. The key is saved immediately and a connection test runs automatically — the card turns green on success or red on failure, and a Last checked timestamp is displayed. You can also click Test Connection at any time to re-run the check with the stored key.
How Test Connection works: All API tests run through the app's backend server to avoid browser security restrictions (CORS). Results include the exact error code and a direct link to the provider's developer portal if your key is rejected. Every card preserves the last result and timestamp so you can see which services were verified most recently.
Automatic connection checks: When you open the Settings page, databases that do not require a key — OpenAlex, HAL, arXiv, PubMed (optional key), and ACM Digital Library (optional key) — are tested automatically in the background every time the page loads. Their cards update with a live result and a fresh Last checked timestamp without any button click. Key-required databases (IEEE, Scopus, etc.) are also auto-tested on page load when a key is already saved, and again automatically after you click Save Key — so you always see the result immediately without a separate click.

15. Research Evaluation Survey

The Research Survey page contains a structured research evaluation questionnaire designed for academic user studies assessing RSP's usability and impact.

Survey structure:

  • Section A — Participant Background: Optional demographic info (role, experience, field)
  • Section B — System Usability (SUS): 10 questions on a 1–5 Likert scale, based on Brooke (1996)
  • Section C — Perceived Usefulness & Ease of Use: 8 questions on a 1–7 scale, based on TAM/UTAUT
  • Section D — Impact on Research Quality: 7 questions on transparency, reproducibility, and bias
  • Section E — Feature-Specific Evaluation: 5 questions rating individual features
  • Section F — Open Feedback: 5 free-text questions for qualitative insights

How it works:

  • A progress bar at the top tracks how many Likert questions have been answered (30 total)
  • All required questions must be answered before submission
  • Clicking Submit Survey validates the form and sends the responses to the study's response collector:
    • Responses are recorded regardless of whether SMTP is configured, so participants can submit on a fresh installation
    • SMTP configured — the study owner additionally receives an email with the full response attached as a CSV
    • If the submission cannot be delivered — a modal offers " Open in My Email App" (opens Outlook, Apple Mail, Gmail, etc. with all responses pre-filled) or " Configure SMTP in Settings" so nothing is lost
  • Clicking Start Over resets all fields after confirmation
Tip: The survey is designed for ethics-approved user studies. All responses are anonymous unless the participant voluntarily provides identifying information.

17. SLR Workflow Best Practices

Follow this recommended workflow for a systematic literature review using RSP:

Figure 13: Recommended SLR workflow with RSP

Key principles:

  • Start broad, then narrow — Begin with no filters, add criteria progressively
  • Always validate — Use validation papers as your ground truth after every change
  • Monitor PRISMA — Click the stage cards and excluded cards to inspect exactly which papers were removed at each stage
  • Document post-inclusion steps — Record full-text decisions per paper; use Manual Review Steps for additional steps, taking care not to count full-text exclusions twice.
  • Review the checklist — Verify all items against the report, add notes, and confirm those addressed before exporting
  • Check coverage before reporting — Use PRISMA numbers only from a run in which the Database coverage table shows every database Complete; re-run all databases together after fixing a failed or partial one, so every count has the same search date
  • Save early, save often — Save your search configuration for reproducibility
  • Export and verify — The replication package helps document your review; check its contents, evidence and any provider restrictions before sharing.

Performance notes:

  • Retrieval limits are adjustable per database in Settings → Retrieval. Some APIs and connectors have additional pagination or quota limits — RSP shows an amber partial-retrieval warning when a database could not deliver everything it found. Narrow the query for that database if completeness matters
  • arXiv has rate limiting — a 3-second delay between result pages is applied automatically; avoid rapid consecutive searches
  • HAL supports more server-side filters (language, doc type, year) which are faster than post-filtering
  • Searches stream results database by database via SSE — you see progress live as each database completes

Data storage:

  • Search form state & results — browser localStorage (persists across navigation). Large result sets that exceed the browser's storage limit are reloaded in full from the saved run in data/results/adhoc/, so the result list, exports and Print to PDF always cover every result
  • Excluded paper lists — browser localStorage (lastExcludedDocs) — enables clickable PRISMA excluded cards
  • PRISMA manual steps, snowballing & checklist — stored with the corresponding run on the server and removed with that run. Older browser data can be explicitly imported.
  • Validation papers — browser localStorage
  • Saved searches & history — server-side JSON files in data/ folder
  • API credentials — stored as plain text in data/ and sent to the relevant provider when required. Protect this folder; do not share or commit it.
  • Retrieval settings — data/retrieval_settings.json (year range at the database, per-database maximums)
  • Feedback attachments — only if their upload failed: data/feedback_attachments/ (one folder per submission; safe to delete once reported)
Need help? RSP is designed to be self-explanatory. Each page includes contextual hints. If you encounter issues, restart the application with its launcher (STOP then START.bat / start.command, or the Docker stop/start scripts) and check the error messages in rsp.log in the RSP folder (Docker: docker compose logs). To report a problem, use the Feedback page and attach a screenshot and rsp.log.
Community support: RSP is free and will remain free. If it helps your work, optional support is available via the footer link and on the About page.
